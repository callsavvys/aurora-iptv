## Problem Statement

The owner built a new keyboard-driven interface in `web/` (about 2,600 lines: Home, Movies, Series, Live TV, My List, Search, Settings, title and person pages, player, TMDB enrichment, Xtream sources), tried it on the Mac against a real 498-category line, and approved it: "okay this one is close i like it". The Android TV app still ships the old `app/renderer.js` (4,437 lines). The goal is that a person who updates the TV app with Downloader code 8502133 gets the new interface, keeps their saved line, account and history, and loses nothing the old TV app did.

## What Makes This Cool

The TV becomes the first platform on one modern, modular codebase built around a focus engine for the D-pad, instead of a monolith that rebuilds `innerHTML` wholesale (the pattern that silently broke adding a friend by code). The Mac and iPhone follow later from the same code.

## Constraints

- Every TV user upgrades in place. The APK must be signed with `mobile/android-release.keystore`, and the release must keep an `Aurora-TV.apk` asset so Downloader 8502133 picks it up.
- No data loss. The old app keeps prefs (including My List as `favorites` and watch `progress`) and secrets in Capacitor Preferences under the `prefs` and `secrets` keys. The new app keeps them in their old shape and never deletes them, so going back to an old APK still works.
- `web/` currently needs `web/server.cjs` for `/api/proxy`, `/config.js` and `/vendor/hls.js`, and keeps the Xtream password in `localStorage`. None of that may ship to the TV as is.
- TV hardware: a 960×540 CSS px viewport, low-end WebView, a held D-pad arrow. Focus movement over ~100 ms feels sluggish.

## Premises (agreed)

1. The right problem is shipping the approved `web/` interface to the TV without data loss. Doing nothing leaves TV users on the interface the owner has moved past.
2. The TV network path is proven: the old TV app already plays live HLS through hls.js with CapacitorHttp patching XHR (`app/renderer.js:2460`, `relay = url` when native). `web/` can call providers directly on the TV with no proxy.
3. The old TV app's state lives in two Capacitor Preferences keys that `mobile/platform/platform-native.js` reads with `read("prefs")` and `read("secrets")` (lines 31–35). `prefs` holds `favorites` (item ids), `progress` (keyed records with `updatedAt`), `favoriteTimes`, `progressGone`, `syncDirty`, `syncCursor`, `activeSource`, `theme` and a few others. `secrets` holds `sources`, `auth` (the Supabase session, under storage key `aurora-auth`), `vault`, `tmdb` and `omdb`. The new platform layer reuses that Preferences and secrets handling rather than writing a new one.
4. The default build flips to `web/` only after all six parity features exist: accounts and Supabase sync, profiles and the who-menu, History, the live guide, the update notice, and friends and Together. The owner chose this over shipping without Together: "loses nothing" wins over speed.
5. Distribution is covered by the existing release path: a GitHub Release with an `Aurora-TV.apk` asset, picked up by Downloader 8502133.

## Landscape

- Capacitor apps on Android are reported to run slower than the same app in a browser ([capacitor#3899](https://github.com/ionic-team/capacitor/discussions/3899)). Measuring on the real TV is the only reliable check.
- Fixed-size windowing with 2–3 rows of overscan is the standard approach for long TV lists. The known failure is losing focus when the focused row is unmounted, so the browser resets focus to `body` ([perf-virtual-lists](https://playbooks.com/skills/dbobkov245-source/pwa-torserve/perf-virtual-lists)).
- CapacitorHttp patches both `fetch` and `XMLHttpRequest` when enabled ([Capacitor HTTP docs](https://capacitorjs.com/docs/apis/http)). This matches what the old TV app already relies on.

The conventional wisdom holds here.

## Approaches Considered

### Approach A: Port into web/ (chosen)
A platform layer and a build switch make `web/` the TV app. The six parity features are rebuilt as `web/` modules on its focus engine. XL effort, medium risk. Reuses `platform-native.js`, `focus.js`, the Supabase schema and the old Preferences keys.

### Approach B: Reskin the old renderer
Rejected: it keeps the 4,437-line monolith, and the owner approved `web/`'s behaviour, not only its look.

### Approach C: Side-by-side "Aurora Next" APK
Rejected: Android sandboxes two packages, so the new app could not read the old one's Preferences without an export step, and there would be two apps to maintain.

## Recommended Approach

Approach A, as laid out in `docs/plans/web-ui-to-tv.md`, with these decisions:

1. **Platform layer.** `web/js/platform.js` is the only module that knows where it runs: `net.get`, `streamUrl`, `storage`, `config`, `onBack` and `version`.
   - `platform-native.js` is split in two. `platform-core.js` builds `window.aurora` (Preferences, secrets, back button, update check) and sets `window.auroraReady`, a promise that resolves once the prefs and secrets snapshots are read. `platform-boot-app.js` holds today's tail (lines 169–179), which loads `renderer.js` and then `tv-nav.js`, plus `fitToScreen`.
   - The `app/` build stages both files in the same order as today, so it behaves the same. A test checks that `www/index.html` for the `app/` build still loads the renderer and the D-pad layer.
   - The `web/` build stages only `platform-core.js`. `web/index.html` loads a small `boot.js` that awaits `window.auroraReady` (resolved immediately in a browser) before importing `js/app.js`, so nothing reads storage before the snapshot exists.
2. **Screen model.** `web/` lays out natively at the WebView's 960×540 CSS px. `fitToScreen` and the 1920-wide zoom stay in `platform-boot-app.js` and are never loaded by the `web/` build. The tests, the 40 px focus-room check and the CDP trace all run at 960×540 with no zoom.
3. **Build switch.** `build-android.sh` gains `AURORA_TV_UI=web`, which stages `web/`, `hls.min.js`, `platform-core.js`, `boot.js` and a generated `config.js`. The TMDB and OMDb keys come from one small script, `scripts/extract-keys.cjs`. It applies the regexes `web/server.cjs` uses today against `app/renderer.js`, and `server.cjs` is changed to call it too. The build fails if either key comes back empty. The default stays `app/` until parity and tests pass.
4. **One store, not an import.** On the TV, the `web/` app reads and writes the old app's own `prefs` and `secrets` Preferences keys, in the old shape.
   - Every write is read-modify-write and keeps fields it doesn't know about.
   - Web-only data goes under new keys of its own: `web.prefs` (language, region, motion, titles) and `web.tmdb` (TMDB match cache).
   - Because both apps use the same records, there is no first-run import and no round trip to lose. Data added in the new app is there after a downgrade, and data added in the old app is there after the next upgrade.
   - My List writes go through the same bookkeeping the old app does: `favorites` holds item ids, `favoriteTimes` records when each changed, and `syncDirty` marks it for upload.
   - Progress records keep the old app's shape and rules (`app/renderer.js` 1037–1065, 2723–2731):
     - **Record.** A record is the old playback record, not a library item (`app/renderer.js` 2490, 2496, 2515), together with `position`, `duration` and `updatedAt: Date.now()`.
       - Movie and live: `{key: id, id, type: "movie"|"live", title, subtitle: category, poster}`.
       - Episode: `{key: "episode-<episodeId>", id: seriesItemId, type: "episode", title: seriesName, subtitle: "S<s> E<n> • <episode title>", poster, seriesId: streamId, season: String(season), episodeId, container, next: {season, episodeId, number, title, container} | null}`.
       - The web adapter maps its own fields onto these names: its `title` becomes `title`, its `kind` becomes `type`, its `poster` becomes `poster`. It never writes `name` or `at`.
       - Live channels are recorded with `position: 0, duration: 0`.
       - The fixture test asserts each of these fields for a movie, a live channel and an episode.
     - **Merging.** A write merges onto the existing record (`{...old, ...patch, updatedAt}`) and deletes `hidden`, because watching something again brings it back to Continue watching.
     - **Removing a Continue watching card.** This sets `hidden: true` with a new `updatedAt` and keeps the record, so the watched mark and the History entry survive. Deleting a record and writing `progressGone[key]` happens only when the user forgets an item from History, as the old app does.
     - **Cap.** After every write the map is capped at 3,000 records. Live entries go first, then the oldest by `updatedAt`.
     - **Sync.** Every progress change marks `syncDirty.progress[key]`.
   - `web/js/store.js`'s `progress` and `myList` become thin views over these records. Continue watching filters out `hidden` records. History is all of them. My List resolves `favorites` ids against the loaded library.
   - The `web/` Xtream adapter must produce the same item ids and progress keys as the old library. A fixture test runs both apps' writers against one captured `prefs` snapshot and one provider reply. It compares the whole `favorites` array and whole progress records, field by field, after a play, a resume, a hide and a forget, and checks that the old renderer can read the new app's `prefs` back.
   - In the browser, `storage` keeps the same shape in `localStorage` under `aurora-web`.
5. **What an upgraded user keeps, and from where:**

   | State | Old app keeps it in | New app |
   |---|---|---|
   | Sources and logins | `secrets.sources` `[{id, name, server, username, password, count, updatedAt}]` | Uses the list as is: several sources, one active |
   | Active source | `prefs.activeSource` (falls back to the first source) | Same key, same fallback |
   | Account session | `secrets.auth["aurora-auth"]` | The same Supabase storage adapter over `secrets.auth`. The user stays signed in. There is one refresh token shared by one installed app, so nothing is copied and nothing can be revoked by a copy. |
   | Vault key | `secrets.vault` | Same key |
   | My List, progress, History | `prefs.favorites`, `prefs.progress`, `favoriteTimes`, `progressGone` | Same keys. History is a view over `progress`, as it is in the old app. |
   | Sync position | `prefs.syncCursor`, `prefs.syncDirty` | Same keys, so the first launch of the new app continues the old cursor rather than starting a first sign-in |
   | Social profile (name, friend code) | Supabase, through `claim_profile` | Fetched after sign-in, as the old app does |
   | Theme | `prefs.theme` | Read, and mapped to the nearest `web/` theme |
   | Library cache | IndexedDB `items:<sourceId>` | Not reused. The new app refetches from the provider and shows its loading message. |

   A source with no `server` or `username` stays in the list. Settings marks it "needs its login again" and opens its edit screen, and it is never dropped. With no sources, the demo source shows, as today.
6. **Sync.** Port the old rule unchanged: per item, the newest `updated_at` wins (against `favoriteTimes[id].at`, or `progress.updatedAt`/`progressGone`). Upload uses the `push_favorites` and `push_progress` RPCs in batches of 500, and download pages through `favorites` and `progress` from `syncCursor`. Local data is never replaced wholesale by the cloud copy.
7. **Feature inventory before parity work.** Before step 8, write `docs/plans/tv-feature-inventory.md`: every feature reachable on the old TV app (views, player controls, settings, tests in `npm test`), each marked present, ported, or accepted gap. Gaps already known beyond the six:
   - player audio and subtitle track menus, and subtitle display (`app/renderer.js` 2658–2675; `web/js/app.js` has none);
   - the preview's connection limits on the provider (`tests/cliffhanger.cjs`);
   - the billboard's rotation (`tests/billboard.cjs`).

   These join the parity list. The flip gate is "every inventory row is present or ported", not only the six.
8. **Parity in order:** accounts and sync, profiles and who-menu, History, live guide (`get_short_epg`), update notice, friends and Together, then the inventory rows from step 7.
9. **TV performance.** Virtualized Live TV lists (about 40 rows around the focus, with focus kept on the logical item across re-renders), TMDB `w342` posters, no `backdrop-filter`. The budget is under 100 ms from press to frame, and 60 fps on a held arrow.
   - It is measured with a CDP trace on the real TV, from a trace build: `AURORA_TRACE=1 bash scripts/build-android.sh` sets `android.webContentsDebuggingEnabled: true` in the staged Capacitor config.
   - Without `AURORA_TRACE`, the script asserts the flag is absent or false before `assembleRelease`, so the shipped 0.39.0 APK cannot be inspected.
10. **Tests at 960×540:** the ported tv-nav, sweep and chrome tests, the 40 px focus-room check, and a keyboard-only walk of Live TV, Search and Settings.
11. **Release 0.39.0** with the `Aurora-TV.apk` asset, signed with the release keystore.
    - The version comes from the root `package.json`, which the Mac app shares. The Mac updater (`updates.asset` = `Aurora-IPTV-Mac-Apple-Silicon.zip`) and the TV notice both read `releases/latest`.
    - So the 0.39.0 release carries both assets: `Aurora-TV.apk` and a Mac zip built from `app/` at 0.39.0. The Mac updater finds its asset, and the TV notice tells 0.38.x TVs to update.

### R3-1 — feasibility (blocking)

**Problem**

> The record schema the design now specifies is wrong. In app/renderer.js a progress record is not the library item: each play site builds a playback record and startPlayback spreads it into state.playing (line 2444), which saveProgress stores. For movies and live it is {key: item.id, id, type, title: item.name, subtitle: item.category, poster: item.logo} (lines 2490, 2496); for episodes it is {key: `episode-${episode.id}`, id: item.id, type: 'episode', title, subtitle: 'S.. E.. • ..', poster, seriesId: item.streamId, season, episodeId, container, next: nextHint(queue)} (line 2515). Library items carry name, logo and streamId and no key. The old app reads title, poster, subtitle, seriesId, season, episodeId, container and next back from records (historyShows 1097-1115, upNextFor 1089-1095, recordFromHint 1082-1085, playRecord 2527-2544). A web writer that stores the library item with `name` would give the old APK after a downgrade History and Continue watching cards with no title or poster, episodes it cannot resume, and no next-episode hint, contradicting the 'old shape' and 'no round trip to lose' promises.

**Remedy**

> Replace the record description with the old playback-record fields per type: movie/live {key, id, type, title, subtitle, poster}, episode adds {seriesId, season (string), episodeId, container, next: {season, episodeId, number, title, container}}, plus position, duration and updatedAt; and say the web adapter maps its own item fields (title, kind, poster) onto these names. Have the fixture test assert these fields explicitly.
